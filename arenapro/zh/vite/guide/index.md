# 认识 Vite

在 ArenaPro 的 Vite 版脚手架里，你最常接触到的底层工具就是 **Vite**。

在继续往下看之前，可以先从「常见痛点」的角度，快速感受一下这套 Vite 脚手架能帮你解决什么问题：

- **开发别再“卡构建”**：

  - 用 `apc dev` 跑开发服务，改一行代码几乎毫秒级生效；
  - 开发期默认不强制跑完整 TS / ESLint 阶段性检查，不再一保存就被红线打断思路。

- **发布前才“严格体检”**：

  - 用 `apc build` 做正式构建时，才统一跑 TypeScript + ESLint 严格检查；
  - 同时打包 client / server，并按 `.env` / `dao3.config.ts` 配置自动上传到神岛。

- **账号 / 地图配置不用手抄**：

  - 用 `apc login` 一键写入 Token 和 UA 到 `.env`；
  - 用 `apc res` 同步目标地图的资源和最新 API 类型声明，不再来回复制 ID、手动敲请求。

- **单入口 / 多入口一套通吃**：

  - 支持一个项目里配置多套 bundle（不同玩法 / 地图）；
  - 通过 `.env` 选择当前要构建 / 上传的 bundle，或者一次性构建所有启用入口。

- **不再被 VSCode 插件“绑死”**：

  - 所有关键配置都落在 `dao3.config.ts`、`.env`、`vite.config.ts` 中；
  - 你可以在任意编辑器里开发，只把 Arena 当成「远端运行环境」。

- **顺手就能发 NPM 包**：

  - 默认准备好 NPM 友好的导出结构与 `dist/` 目录约定；
  - 一份源码既能跑在神岛，又能打成对外复用的客户端 / 服务端 / 共享工具包。

- **踩过坑后的“社区版最佳实践”**：
  - 汇总了 ArenaPro 社区一线使用者（包括官方搬砖喵）的真实经验；
  - 从「只靠插件的新手体验」升级为更接近专业工程流程的脚手架；
  - 保持足够开放，方便团队根据自己习惯继续二次封装和扩展。

更多能力会在后续章节中逐步展开，实际使用中也可以根据团队需要自行扩展配置。

## 什么是 Vite？

用一句话概括：

> **Vite 是一个面向现代前端的开发服务器 + 构建工具。**  
> 开发时极快启动、按需加载；发布时用 Rollup 生成高性能的生产包。

它有两个核心角色：

- **开发阶段**：本地开发服务器，按需把你的 `.ts` / `.tsx` 等转换成 Arena 能跑的代码。
- **发布阶段**：基于 Rollup，负责把项目打成适合线上运行的 production 包。

在 ArenaPro Vite 脚手架里，这一整套流程已经被集成好，你可以把它理解为：

- 开发时，帮你「实时编译 + 热更新」；
- 发布时，帮你「打出适合 Arena 运行的优化产物」。

你不需要自己从零搭建复杂的构建配置，只需要在正确的位置编写游戏逻辑和界面代码即可。

## Vite 和 Webpack 的核心区别

在这个脚手架里，**Vite 和 Webpack 的角色本质上都是「把 TypeScript 打包成可执行脚本」**，
区别主要体现在构建体验和实现方式上。

### 1. 开发体验与构建速度

- **Webpack 版**：

  - 启动开发环境时，需要先经过一轮完整的打包流程；
  - 项目越大，初次启动和每次增量构建都可能变慢；
  - 热更新更多依赖于 loader / plugin 的实现质量。

- **Vite 版**：
  - 在开发阶段更偏向「按需编译脚本」，结合更快的底层工具链；
  - 对纯 TS 项目也能显著缩短冷启动时间；
  - 保存文件后的重新打包范围更小，反馈更快；
  - **为了优先保证热更新速度，开发期的热更新不会执行 TypeScript 类型检查和 ESLint 检查**，
    这些检查会集中在 `build` 和 `debug` 阶段进行。

对你的直观感受是：

- 同样是改一段 TS 代码、看游戏里是否生效，Vite 版通常会更快给出结果。

### 2. 配置复杂度与可维护性

- **Webpack**：

  - 配置集中在 `webpack.config` 以及各种 loader / plugin 上；
  - 很多历史项目会逐渐堆出一套复杂而难以精简的配置；
  - 调整一处行为，有时需要串联多个插件一起改。

- **Vite**：
  - 更强调「约定优于配置」，默认行为已经覆盖大部分常见需求；
  - 在这个脚手架中，我们用相对精简的 `vite.config.ts` 组合好了 TS 打包、资源处理、入口管理等；
  - 你只需要在少数场景下做增量定制（例如增加别名、挂一个小插件）。

从长期维护角度看：

- Webpack 版更适合已经强绑定在旧配置上的老项目；
- Vite 版更适合希望「配置更轻、演进更容易」的新项目。

同时需要注意：

- Webpack 工作流通常更容易在「开发阶段」就强制跑完 TS / ESLint 等检查，
  开发体验略慢，但错误更早暴露；
- 当前这套 Vite 工作流则把「速度」放在首位，
  允许你在热更新时快速迭代逻辑，再在构建阶段统一做严格检查。

### 3. 在本项目中的定位差异

在我们当前的 ArenaPro 项目里：

- **两者都不是「浏览器运行环境」，而是「打包纯 TS 脚本的工具」**；
- 构建产物最终都会被 Arena 运行时加载执行，而不是直接跑在浏览器页面里；
- 你日常编写的仍然是 TypeScript 模块：

```ts
import { foo } from "./foo";

export function bar() {
  foo();
}
```

不同的是：

- 使用 Vite 时，这些 TS 模块会经过更高效的构建链路；
- 使用 Webpack 时，这些 TS 模块会经过相对传统、但生态成熟的打包流程。

你可以简单理解为：

> 在这个项目中，Vite = 新一代的「TS 打包和开发体验引擎」，
> Webpack = 老牌但稍显笨重的「TS 打包引擎」。

## 脱离 ArenaPro 插件独立使用

这一套 Vite 脚手架**可以完全脱离 ArenaPro 插件运行**：

- 你可以在任何代码编辑器里打开项目（VS Code、WebStorm、Neovim 等）；
- 只要有 Node 环境，就可以像普通 Vite 前端项目一样运行、调试、构建；
- 所有本地类型检查、构建、代码组织能力都可以完全体验。

所以，你可以根据自己的偏好选择工作方式：

- 如果你更在意「纯代码工作流」和编辑器自由度，可以只把它当作一个普通的 Vite 项目来用；
- 如果你在乎「和地图编辑器的无缝联动」，建议配合 ArenaPro 插件一起使用，这样可以同时享受 Vite 带来的高效构建体验和插件带来的整合能力。
