# dev / build / debug 三种命令的使用场景

在 ArenaPro Vite 脚手架中，常见有三种运行 / 构建模式：`development`、`production`、`debug`。  
它们分别对应你最常用的三个命令：`apc dev` / `apc build` / VSCode 调试（debug）（也可以通过 `npm run dev` / `npm run build` 等脚本包装调用）。

这篇文章只讲「**命令层面：什么时候用哪一个？**」。  
如果你想在代码里按模式写分支逻辑，可以再看：

- 《在代码中区分 development / production / debug 模式》

## 1. development：日常开发 / 热更新模式

**典型入口：**

```bash
apc dev
# 或使用 package.json 中封装的脚本：
# npm run dev
```

**使用场景：**

- 日常编码和调试；
- 希望改一行代码就能快速看到效果；
- 不希望每次修改都被类型或 ESLint 问题“打断节奏”。

**行为特征（结合脚手架建议）：**

- 使用 Vite 的 **开发服务器 + 热更新（HMR）**：
  - 修改脚本后，自动局部刷新，几乎秒级反馈；
- 构建结果会自动上传 / 同步到 Arena（根据 `VITE_UPDATE_FILE` 等配置）；
- **不会因为 TypeScript 或 ESLint 错误阻止热更新 / 上传**：
  - 你仍然可以在 Arena 中看到运行效果；
  - 类型和 ESLint 问题交给编辑器自带检查、终端提示来处理。

**适合的工作方式：**

- 把 `apc dev`（或 `npm run dev`）当成“持续跑着”的后台服务；
- 频繁改代码 → 看效果 → 再改；
- 不必每次改动都「先把所有 TS / ESLint 问题清零」。

## 2. production：发布前的严格构建

**典型入口：**

```bash
apc build
# 或使用 package.json 中封装的脚本：
# npm run build
```

**使用场景：**

- 准备发布 /提交版本到线上的前一步；
- 想确认这一版在类型、规范、打包上都是**干净**的；
- CI / 自动化流水线中的构建步骤。

**行为特征：**

- 执行一轮**完整构建**：
  - TypeScript 类型检查；
  - ESLint 检查；
  - 实际打包并产出构建结果；
- **如果 TS / ESLint 出错会中断构建**：
  - 错误会在终端输出；
  - 不会继续产出构建结果，也不会继续上传；
- 构建成功后：
  - 产物写入预设目录（如 `dist/`）；
  - 按脚手架配置，自动同步到 Arena。

**适合的工作方式：**

- 日常开发靠 `apc dev`（或对应的 `npm run dev` 脚本），
- 在「准备提交版本 / 发布之前」跑一遍：

  ```bash
  apc build
  # 或 npm run build
  ```

  - 如果通过，说明这一版在类型和规范上是可接受的；
  - 如果失败，根据错误信息修复再重试。

## 3. debug：本地断点调试模式

**典型入口：**

在 VSCode 调试器中运行。

**使用场景：**

- 希望在本地“像调试普通 Node / 前端项目那样”设置断点；
- 需要逐行单步执行，查看变量值、调用栈等；
- 主要针对你自己的业务代码进行深入排查。

**行为特征：**

- 为 VSCode 调试器等工具预留了合适的构建方式：
  - 保留源码映射（source map），方便断点对齐到源码；
- 你可以通过 VSCode 调试器启动 / 附加，
  - 在本地运行代码，
  - 对自己的项目脚本设置断点、单步调试。

**当前限制（重要）：**

- 目前 **不支持** 对神岛引擎内部实现代码进行调试：
  - 也就是说，你可以调试「自己的业务脚本逻辑」，
  - 但无法“跳进”神岛底层引擎的具体实现。

**适合的工作方式：**

- 用 `debug` 模式来处理那种「用 log 不好查、需要单步跟的复杂逻辑」；
- 仍然配合 `development` / `production`：
  - 开发期常驻 `dev`；
  - 需要精细排查时，用 VSCode 启动 `debug` 配置；
  - 发布前用 `build` 走一遍完整检查。

## 4. 一个推荐的组合使用方式

可以把三种模式简单理解为：

- **development**：
  - 高效迭代、热更新、不强行“卡死”你；
- **production**：
  - 严格把关、上线前体检，一旦有 TS / ESLint 问题就立刻阻止；
- **debug**：
  - 为 VSCode 工具准备的断点调试模式，专门服务于「深入排查」。

推荐日常节奏：

1. 写代码时：一直跑着 `apc dev`（或项目提供的 `npm run dev`）；
2. 功能基本完成、准备合并 / 发布时：跑 `apc build`（或 `npm run build`）；
3. 中途遇到不好查的复杂 bug：
   - 启动 `debug` 调试（如 VSCode 调试配置），
   - 在本地断点跟代码逻辑。

根据项目需要，你也可以在代码中读取 `import.meta.env.MODE`，
让同一份脚本在 dev / prod / debug 下拥有不同的日志、检查或特性开关。
